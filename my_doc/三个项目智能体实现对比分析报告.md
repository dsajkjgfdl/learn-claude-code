# 三个项目智能体实现对比分析报告

生成时间：2026-04-14  
对比对象：
- `D:\study\cccc-main`
- `D:\study\deer-flow`
- `D:\study\learn-claude-code\agents\s_full.py`

## 1. 结论先行

这三个对象不是同一层级的东西，直接比较时要先分清定位：

- `cccc-main` 更像“多智能体协作控制面 / collaboration kernel”。它不自己实现统一的 LLM 主循环，而是把 Claude Code、Codex CLI、Gemini CLI 等外部 runtime 纳入同一个守护进程、账本和消息控制面里。
- `deer-flow` 是“内聚型超级智能体平台”。它把 lead agent、middleware、sandbox、memory、skills、MCP、subagent、custom agent 都放在同一套后端框架里。
- `agents/s_full.py` 是“教学型单文件原型”。它把很多常见机制塞进一个文件中，便于理解和改造，但离生产级系统还有明显距离。

如果只看成熟度和工程完整性：`deer-flow` 最完整。  
如果只看多智能体协作控制面和跨 runtime 协同：`cccc-main` 最有特色。  
如果只看可读性、可快速 hack 和教学价值：`s_full.py` 最直接。

## 2. 总览对比

| 维度 | cccc-main | deer-flow | s_full.py |
| --- | --- | --- | --- |
| 系统定位 | 多 runtime 协作内核 | 集成式超级智能体平台 | 单文件教学/原型框架 |
| 智能体执行形态 | 外部 CLI runtime + 守护进程控制 | LangGraph/ LangChain `create_agent()` + middleware | 直接调用 Anthropic API 的 while-loop |
| 状态持久化 | append-only ledger + group/context/agent_state | `ThreadState` + thread data + memory + artifacts + todos | 本地文件夹 `.tasks/.team/.transcripts` |
| 工具治理 | MCP 能力面 + progressive disclosure | config tools + built-ins + MCP + ACP + deferred tool search | 手写 tool schema + `TOOL_HANDLERS` |
| 多智能体能力 | 强，且是系统核心 | 有 subagent，但仍以 lead-agent 为中心 | 有 teammate/thread，但更像原型 |
| 安全/治理 | 强在消息/控制面；执行安全依赖外部 runtime | 最强，middleware + sandbox + loop guard + clarification interrupt | 最弱，`shell=True` + 简单黑名单 |
| 提示词策略 | 短 system prompt + 外置 help/playbook | 大型动态 prompt template + SOUL/memory/skills/subagent sections | 极简 system prompt |
| 最适合 | 多代理协作、审计、消息可达性 | 一体化 agent 产品/平台 | 教学、实验、快速原型 |

## 3. 实现方案分析

### 3.1 `cccc-main`

**方案概述**

`cccc-main` 的核心不是“我自己实现一个 agent loop”，而是“我提供一个可靠的多智能体协作内核”。  
它的重点是：

- 单写者 daemon、append-only ledger、统一控制面。
- 对多个外部 agent runtime 的统一接入和管理。
- 通过消息投递、read/ack/reply-required、group state、automation 来保证协作可追踪。
- 通过极短的 system prompt + `cccc_help` playbook，把行为约束尽量放到控制面和工具面，而不是把所有规则都塞进 system prompt。

**源码证据**

- system prompt 明确强调“Minimal / No tool docs / Ops playbook lives in MCP”：`D:\study\cccc-main\src\cccc\kernel\system_prompt.py:15-19`
- prompt 只保留身份、group、scope、几个 invariants：`D:\study\cccc-main\src\cccc\kernel\system_prompt.py:88-151`
- 默认 preamble 只有冷启动路线和工作姿态：`D:\study\cccc-main\src\cccc\kernel\prompt_files.py:18-27`
- 长期工作手册在 `cccc-help.md`，覆盖 recall、coordination、agent_state、scope discipline：`D:\study\cccc-main\src\cccc\resources\cccc-help.md:40-130`
- daemon 会做 lazy preamble、消息节流和 MCP reminder：`D:\study\cccc-main\src\cccc\daemon\messaging\delivery.py:1-18`、`D:\study\cccc-main\src\cccc\daemon\messaging\delivery.py:697-715`、`D:\study\cccc-main\src\cccc\daemon\messaging\delivery.py:916-939`
- capability surface 是 progressive disclosure，而不是一次性把全部工具暴露给模型：`D:\study\cccc-main\src\cccc\kernel\capabilities.py:14-40`、`D:\study\cccc-main\src\cccc\kernel\capabilities.py:43-106`
- runtime 侧是多 CLI runtime 编排：`D:\study\cccc-main\src\cccc\kernel\runtime.py:30-89`

**优点**

- 优点 1：协作控制面非常强。它解决的是“多个 agent 是否真的收到了消息、谁看过、谁该回复、状态是否一致”这种很多框架没认真解决的问题。
- 优点 2：prompt 负担很轻。短 prompt + 外置 playbook 的设计，明显更利于长期维护和多 runtime 适配。
- 优点 3：runtime 无关。Claude/Codex/Gemini/Kimi 等都能放进同一机制里，扩展面广。
- 优点 4：能力面渐进暴露。先给核心工具，额外能力按 pack 开启，能减少模型上下文里的工具噪音。
- 优点 5：lazy preamble 和 daemon 驱动消息投递，是很实用的工程细节，说明作者确实在处理真实 runtime 的不稳定行为。

**缺点**

- 缺点 1：它更像“agent OS / control plane”，不是自带执行内核的 agent 平台。真正的执行质量很大程度上取决于外部 CLI runtime 本身。
- 缺点 2：system prompt 之所以短，是因为很多规则都要求模型先调用 `cccc_bootstrap`、再调用 `cccc_help`。如果 runtime 或模型没有严格走这个入口，质量会明显波动。
- 缺点 3：提示词、工具、控制面被故意拆散，工程上是好事，但理解门槛更高，新接入者不容易一次看全。
- 缺点 4：对单智能体本地 coding 场景来说，这套控制面可能偏重，系统价值主要体现在多智能体与远程协作上。

**提示词质量评价**

- 质量判断：高，但“高”是针对协作型场景，而不是传统单 agent 执行 prompt。
- 优点：高信噪比、强约束感、低 token 税、可维护性好。
- 风险：system prompt 本身并不完整，必须依赖 `cccc_help` 和 MCP 控制面；换言之，它是“控制面增强型提示词”，不是“自解释型超级 prompt”。

### 3.2 `deer-flow`

**方案概述**

`deer-flow` 是三者里最“完整的一体化 agent 后端”。  
它不是把 agent 行为外包给外部 CLI，而是自己在后端里组合：

- `create_agent()` lead agent
- `ThreadState`
- runtime middleware chain
- sandbox
- memory
- todo / title / token usage / loop detection
- MCP + ACP
- deferred tool search
- async subagent execution
- custom agent `SOUL.md`

这套设计明显更像“产品级 agent platform”。

**源码证据**

- lead agent 用 `create_agent()` 构造，接 prompt、tools、middlewares、state schema：`D:\study\deer-flow\backend\packages\harness\deerflow\agents\lead_agent\agent.py:273-350`
- middleware 顺序很明确：summarization、todo、title、memory、vision、deferred tool filter、subagent limit、loop detection、clarification：`D:\study\deer-flow\backend\packages\harness\deerflow\agents\lead_agent\agent.py:198-270`
- `ThreadState` 显式承载 sandbox/thread_data/title/artifacts/todos/uploaded_files/viewed_images：`D:\study\deer-flow\backend\packages\harness\deerflow\agents\thread_state.py:48-55`
- 工具装配是 config tools + built-ins + MCP + ACP，并带 deferred registry：`D:\study\deer-flow\backend\packages\harness\deerflow\tools\tools.py:35-137`
- prompt template 会动态拼入 soul、memory、skills、deferred tools、subagent、ACP mounts：`D:\study\deer-flow\backend\packages\harness\deerflow\agents\lead_agent\prompt.py:318-503`、`D:\study\deer-flow\backend\packages\harness\deerflow\agents\lead_agent\prompt.py:674-724`
- subagent 提示词单独定义，并区分 general-purpose / bash：`D:\study\deer-flow\backend\packages\harness\deerflow\subagents\builtins\general_purpose.py:5-48`、`D:\study\deer-flow\backend\packages\harness\deerflow\subagents\builtins\bash_agent.py:5-47`
- `task` tool 后台异步执行 subagent，并把状态/消息持续流回主线程：`D:\study\deer-flow\backend\packages\harness\deerflow\tools\builtins\task_tool.py:22-126`、`D:\study\deer-flow\backend\packages\harness\deerflow\tools\builtins\task_tool.py:141-248`
- clarification 不是纯 prompt 约定，而是 middleware 级中断：`D:\study\deer-flow\backend\packages\harness\deerflow\agents\middlewares\clarification_middleware.py:23-132`
- loop detection 也是 runtime 级，而不是只靠 prompt：`D:\study\deer-flow\backend\packages\harness\deerflow\agents\middlewares\loop_detection_middleware.py:1-12`、`D:\study\deer-flow\backend\packages\harness\deerflow\agents\middlewares\loop_detection_middleware.py:131-296`
- custom agent 可以通过 `config.yaml` + `SOUL.md` 定制：`D:\study\deer-flow\backend\packages\harness\deerflow\config\agents_config.py:18-29`、`D:\study\deer-flow\backend\packages\harness\deerflow\config\agents_config.py:77-94`

**优点**

- 优点 1：工程完整度最高。状态、工具、sandbox、memory、subagent、custom agent、tool error handling 都在一个统一框架内，行为更可控。
- 优点 2：prompt 和 runtime enforcement 对齐得比较好。比如 clarification、loop detection、subagent limit 都不是“只写在 prompt 里”，而是有 middleware 兜底。
- 优点 3：扩展方式清晰。SOUL、skills、tool groups、deferred MCP tools、ACP agents 都有可插拔边界。
- 优点 4：subagent 设计比 `s_full.py` 成熟很多。它有独立配置、后台执行、流式事件、取消与超时处理。
- 优点 5：相对容易产品化。它天然适合做 Web UI、线程隔离、上传文件、输出 artifacts、用户可见的 todo/title 这些面向产品的能力。

**缺点**

- 缺点 1：复杂度最高。行为被分散到 prompt、middleware、tool、config、state schema 多层，排障成本也最高。
- 缺点 2：prompt 太重。`SYSTEM_PROMPT_TEMPLATE` 本身就很长，再叠加 memory/skills/subagent/deferred tools，会有不小的 token 税。
- 缺点 3：规则有重复和叠层。比如 clarification、todo、subagent orchestration、citations 等同时存在于 prompt 和 runtime 逻辑中，后续维护要非常小心，不然容易产生“规则看似一致、实际微妙分叉”。
- 缺点 4：提示词里“Clarification First”非常强硬，在很多 coding 场景下可能会偏保守，降低自主推进能力。
- 缺点 5：citation block 对 research 很好，但在纯 coding/ops 场景里会增加无关负担。

**提示词质量评价**

- 质量判断：高，但偏重。
- 优点：覆盖面完整、执行例子充分、对工具和 subagent 的指令非常具体、定制能力强。
- 风险：信息量过大、重复的 “CRITICAL” 规则过多，可能造成信号稀释；某些规则是“全局始终开启”的，但其实只在特定任务类型下有价值。
- 一句话评价：`deer-flow` 的 prompt 不是不强，而是“太强、太满、太重”，优点是可控，代价是维护和 token 成本。

### 3.3 `agents/s_full.py`

**方案概述**

`s_full.py` 的设计目标很明显：把常见 agent 机制压成一个可以直接跑的教学样本。  
它的核心形态是：

- 一个 Anthropic `messages.create()` while-loop
- 一组本地 tools + `TOOL_HANDLERS`
- 本地文件任务板
- 背景线程
- 本地 teammate thread
- LLM 驱动的上下文压缩

它非常适合理解“原型 agent 是怎么拼出来的”，但不适合直接当生产方案。

**源码证据**

- 文件头把自己定义为 “Capstone Teaching Agent”，并宣称合并了 `s01-s18` 的机制：`D:\study\learn-claude-code\agents\s_full.py:3-33`
- `run_bash()` 使用 `shell=True`，只靠字符串黑名单阻断危险命令：`D:\study\learn-claude-code\agents\s_full.py:136-149`
- `run_subagent()` 本质上是同一模型、同一进程内再起一个小循环，不是真正隔离执行环境：`D:\study\learn-claude-code\agents\s_full.py:221-256`
- `SkillLoader` 是一个很轻的 frontmatter 解析器：`D:\study\learn-claude-code\agents\s_full.py:259-284`
- `auto_compact()` 直接让模型总结历史以续上下文：`D:\study\learn-claude-code\agents\s_full.py:317-349`
- `TaskManager` 是本地 JSON 文件任务板：`D:\study\learn-claude-code\agents\s_full.py:353-416`
- `TeammateManager` 用 thread + inbox 文件模拟持久化 teammate：`D:\study\learn-claude-code\agents\s_full.py:491-623`
- 主 system prompt 只有三行核心指令：`D:\study\learn-claude-code\agents\s_full.py:645-648`
- 主循环是典型的 `LLM -> tool_use -> 执行 -> tool_result -> 继续`：`D:\study\learn-claude-code\agents\s_full.py:745-802`
- 文件头写了 `PermissionManager`、`HookManager`、`MemoryManager`、`build_system_prompt()`、`WorktreeManager` 等映射，但对这些标识符做源码搜索时，只能在文件头注释里找到，没有实际实现定义。

**优点**

- 优点 1：可读性极强。一个文件就能看懂主循环、工具分发、subagent、压缩、任务板、队友线程这些基础结构。
- 优点 2：非常适合教学和快速实验。要加一个工具、改一个协议、试一个 prompt，改动成本很低。
- 优点 3：本地文件式状态足够直观，便于调试。
- 优点 4：已经展示了一些很实用的小模式，例如大输出落盘、自动 compact、background command、file-based task board。

**缺点**

- 缺点 1：安全性明显不够。`run_bash()` 使用 `shell=True`，黑名单式拦截太脆弱，远不是真正的 permission/sandbox 设计。
- 缺点 2：真正的隔离不足。subagent 只是复用同一模型 API 再跑一层 loop，teammate 也只是线程 + 文件 inbox，不是独立 runtime。
- 缺点 3：头部声明与真实实现有漂移。作为教学样本可以理解，但如果把它当完整框架，就会高估它的能力边界。
- 缺点 4：缺少工程化护栏。没有像 DeerFlow 那样的 loop guard、clarification interrupt、tool error middleware、state schema、真正的 sandbox 生命周期。
- 缺点 5：全局可变对象很多，后续一旦并发复杂起来，状态一致性和线程安全会很脆弱。

**提示词质量评价**

- 质量判断：中低。
- 优点：极简、token 成本低、不会用 prompt 把模型压得太重。
- 缺点：过于简短，缺少澄清策略、风险策略、完成定义、验证要求、输出风格边界、异常处理指引。
- 一句话评价：它更像“代码补 prompt”，不是“工程化 agent prompt”。

## 4. 三者的提示词质量横向比较

这里说的“提示词质量”，不是只看长短，而是看：

- 指令是否清晰
- 是否和运行时机制对齐
- 是否容易维护
- token 成本是否合理
- 是否会把模型过度束缚或过度放飞

| 维度 | cccc-main | deer-flow | s_full.py |
| --- | --- | --- | --- |
| 指令完整性 | 中上 | 高 | 低 |
| 指令清晰度 | 高 | 中上 | 中 |
| 与 runtime 对齐度 | 高 | 很高 | 中低 |
| token 效率 | 很高 | 低 | 很高 |
| 可维护性 | 高 | 中 | 中 |
| 过度约束风险 | 低 | 中高 | 低 |
| 缺少护栏风险 | 中 | 低 | 很高 |

**我的判断**

- `cccc-main`：提示词设计最“克制”。它把长期规则外置到 `cccc_help`，把能力发现外置到 capability 面，是一种很成熟的 prompt/control-plane 分层思路。
- `deer-flow`：提示词内容最“强”。如果你想把模型往稳定、可控、少犯错方向推，它很有效；但它已经接近“超级操作手册”的规模了。
- `s_full.py`：提示词最“轻”。轻是优点，也是短板；教学上合适，生产上不够。

## 5. 该怎么选

**如果你的目标是多智能体协作和可审计控制面**

- 优先看 `cccc-main`。
- 它的核心价值不是“单个 agent 有多聪明”，而是“多个 agent 如何被可靠组织起来”。

**如果你的目标是做一个内聚的一体化 agent 产品**

- 优先看 `deer-flow`。
- 它更像一个完整平台，适合做 Web 产品、线程隔离、文件上传、subagent、memory、custom agent 等一整套体验。

**如果你的目标是快速做实验、教学或搭一个可改的最小原型**

- `s_full.py` 最合适。
- 但建议把它当“学习样本”，不要直接把它当生产基线。

## 6. 如果要吸收三者优点，最值得借鉴的点

- 从 `cccc-main` 借鉴：把协作控制面、消息可靠性、能力渐进暴露做成系统层，而不是全靠 prompt。
- 从 `deer-flow` 借鉴：把 clarification、loop detection、subagent limit、tool error handling 这些高风险行为做成 middleware/runtime enforcement。
- 从 `s_full.py` 借鉴：把原型做得足够直观，先把主循环和状态流跑通，再逐步抽象。

## 7. 我会优先改进的地方

**对 `cccc-main`**

- 增加一个更显式的“首轮必经 bootstrap/help”运行时兜底，而不是主要依赖 prompt。
- 给弱模型一个可选的 condensed tool guide，降低对 runtime 自带 MCP 理解能力的依赖。

**对 `deer-flow`**

- 把超长 prompt 再拆层：研究类、coding 类、运维类的规则按任务类型注入，而不是长期全量注入。
- 把 citation、clarification、subagent orchestration 这几块再降重复，减少 prompt 和 middleware 双份维护。

**对 `s_full.py`**

- 先修正文档映射漂移，避免“文件头说有，但代码里没有”。
- 尽快把 `run_bash()` 从字符串黑名单升级到真正的 permission/sandbox 机制。
- 把 prompt 从三行扩展成最小可用版：补上澄清、验证、风险确认、完成定义。
